# Migrations & Data Model Rules

## How the schema is built (important invariant)

Dev/test/local-compose build the schema from **`SQLModel.metadata.create_all`**
(`init_db`), NOT by running migrations. Production applies migrations on top of
an existing schema. The two must agree, and CI checks that they do (#1057): the
"Migration chain" step in `ci.yml` builds a database with `alembic upgrade head`
from empty, round-trips the newest migration (`downgrade -1`, `upgrade head`),
then runs `scripts/check_migration_drift.py`, which fails on any difference
between that schema and the models.

When the drift check fails, one side changed without the other: add the missing
migration, or change the model to match what the chain (and so prod) has. Put a
difference in the script's `KNOWN_DRIFT` only if it is deliberate, with the
reason. Blind spots: server defaults, triggers/functions (see below), and a
VARCHAR with no length in the model compares equal to any length, so give
string columns the `max_length` the migration uses.

An irreversible downgrade must warn and do nothing, not raise (see
`b8d1f04e37a2`): CI round-trips the newest migration, and an operator rolling
back the schema underneath it must not be blocked.

Consequence: **every table needs both a SQLModel model AND a migration.** A
migration-only table is invisible to `create_all` and silently absent in dev
(this bit us with `email_quota`, now modeled as `EmailQuota`). A model-only
table exists in dev and test but not on a database built from the chain
(`activationtoken`, `refreshtoken` and `audit_log` were, until d84645c6404c).
`test_every_model_table_is_created_by_a_migration` in `tests/test_migrations.py`
fails on the second case. When you add a table, add both.

The same applies to any schema object that is not a table — indexes are handled
by SQLModel, but triggers and functions are not. Attach them to the table's
`after_create` event so `create_all` installs them, *and* emit them from the
migration for production. `Job.closed_at`'s trigger (`models/jobs.py`) is the
worked example, and `tests/test_migrations.py` asserts the two copies have not
drifted.

**`create_all` only creates what is missing — it never alters what exists.** So
pulling a branch that adds a column or a trigger does nothing to a database you
already have: you get `UndefinedColumn` errors until you recreate it.

```bash
docker compose down -v && make services   # drop the volume, rebuild the schema
uv run python scripts/seed_mock_data.py   # optional: repopulate
```

If `docker compose ps` prints nothing while `docker ps` shows `rs-recruiting-*`
containers running, they belong to a different compose project and `down -v`
above is a silent no-op — you will recreate nothing and still see the old
schema. The compose services set an explicit `container_name`, so containers
started from another directory collide by name rather than coexisting, which
also shows up as `make services` failing with "container name is already in
use". Find where they came from and tear them down there:

```bash
docker inspect rs-recruiting-db \
  --format '{{index .Config.Labels "com.docker.compose.project.working_dir"}}'
```

Production is unaffected — it runs the migration chain, which does alter in
place.

## Alembic safety

**Always preview before applying:**
```bash
uv run alembic upgrade --sql head   # review SQL output first
uv run alembic upgrade head         # only after reviewing
```

A `PreToolUse` hook in `.claude/settings.json` blocks any `alembic upgrade`
without `--sql` from Claude. This is intentional: Claude generates and previews
migrations; **applying them is a human step** — ask the user to run the apply
command themselves.

- Never auto-apply a migration without reviewing the generated SQL
- Never squash or delete migrations that have been applied to production
- After adding a nullable→non-nullable column, always provide a server_default or a data migration step
- Migration files: `alembic/versions/` — autogenerated names are fine, but add a short description

## SQLModel / SQLAlchemy patterns

### Eager loading (N+1 prevention)
Use `selectinload` **at the call site**, not on the model relationship:

```python
select(Job)
    .options(selectinload(Job.company).selectinload(CompanyProfile.user))
    .where(Job.id == job_id)
```

Model-level `lazy="selectin"` pollutes every query that loads the parent — even list endpoints that don't need child rows. Only use model-level eager loading when the relationship is needed on **every** access path without exception.

For one-shot joins where no SQLModel relationship exists (e.g. `ActivationToken → User`), a plain `.join()` returning a tuple is fine.

### Async safety
All DB calls must be `await`ed. Never use sync SQLAlchemy sessions in async route handlers. The session is provided via `get_session` dependency — never instantiate it manually in service functions.

## Schema changes checklist
1. Write the Alembic migration (`uv run alembic revision --autogenerate -m "description"`)
2. Review the generated file — autogenerate misses some things (constraints, indexes, enum changes)
3. Run `uv run alembic upgrade --sql head` and read the output
4. Apply: `uv run alembic upgrade head` — human-run; the settings hook blocks Claude from applying
5. Update the model in `libs/shared/rs_shared/models/` if the migration adds/removes columns
